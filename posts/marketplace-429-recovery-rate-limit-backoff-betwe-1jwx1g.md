# Marketplace 429 Recovery — Rate Limit Backoff Between Image Creation and Storage Upload

Short answer: treat image generation and object persistence as separate state transitions, retain one recoverable artifact between them, and retry only the transition that failed; a `429` must never cause a marketplace worker to generate a second image or write into another tenant's namespace.

This is an architecture decision, not a choice of a clever backoff formula. Once an image exists, the system has crossed a boundary that a queue retry cannot reconstruct safely unless the generated bytes, or a durable handle that can retrieve the exact bytes, survive the worker attempt. The export path adds a second constraint: ownership must come from an authorized database record, not from a filename, request field, or loosely matched object prefix.

## Decision and invariants

Use two independently retryable operations: `GENERATE` produces an artifact record and a recoverable payload; `PERSIST` copies that exact payload to a deterministic, tenant-derived object key. A worker acknowledges generation only after the artifact can be recovered by a later worker. The final object write may be repeated, but generation may not be repeated merely because persistence failed.

That yields four invariants:

1. One logical asset has one immutable `asset_id`, assigned before either external call.
2. The server derives `tenant_id` from the authenticated job envelope and checks the product belongs to that tenant; it doesn't accept ownership from generated metadata.
3. The final key is deterministic, for example `tenants/{tenant_id}/products/{product_id}/{asset_id}.png`.
4. An export enumerates committed asset records scoped by `tenant_id`; it does not scan an untrusted prefix supplied by the caller.

An object key is an address, not authorization.

These invariants matter more than nominal queue delivery semantics. A duplicate delivery, a process exit between remote success and local acknowledgement, or a delayed retry should converge on the same asset record and the same object key. If the storage interface supports a conditional create, use it to reject an unexpected pre-existing value; otherwise, compare the stored checksum and size before treating an existing object as the intended result. The precise conditional mechanism varies by storage implementation, so I'm not sure a portable adapter can promise it without exposing capability flags. Test the actual adapter contract.

## How should a queue retry after a 429 when image creation succeeds but object storage upload fails?

First, record which operation emitted the `429`. A generation rate limit means the image does not yet exist, so the `GENERATE` transition can be rescheduled. A storage rate limit during `PERSIST` means the artifact already exists, so only the upload is rescheduled. Combining both under a generic `throw and retry job` handler is the common structural mistake: the queue knows an attempt failed, but it doesn't know which side effect already committed.

Retry the transition.

Honor a valid server-provided retry delay when one is available; otherwise, use bounded exponential backoff with jitter. The bound is operational policy, not a universal constant. It should be long enough to stop synchronized workers from hammering the same dependency and short enough to meet the marketplace's asset-publication objective. Don't hold a queue worker open while waiting. Persist `next_attempt_at`, release the worker, and let the scheduler claim the transition later.

Retry classification must also be narrow. Rate limiting and transient transport failures may be retried. Authentication failures, invalid object keys, unsupported media, tenant mismatches, and exhausted retry budgets require a terminal state or operator review because another delay cannot repair their input. Avoid the alluring rule that every non-success response is transient — it turns a malformed job into background traffic with no completion path.

There is a harder failure: the generator reports success, the worker receives bytes, and the process exits before those bytes reach durable staging. No backoff policy repairs that gap. The generation service must provide a durable result handle, or the system must stage the bytes before acknowledging the transition. If neither property exists, document at-least-once generation as a limitation and reconcile duplicate provider results by `asset_id`; don't call the workflow exactly once.

Consider the concrete ordering, because broad labels such as "the image job failed" hide it. At `10:00:00`, worker A claims asset `a-184`; at `10:00:03`, generation returns bytes; at `10:00:04`, the first final-object write is rate-limited; and at `10:00:05`, the worker exits. If `a-184` already points to a durable staged artifact, worker B can claim `PERSIST`, use the same checksum and destination, and finish. If the bytes existed only in worker A's memory, worker B has no input to upload. The tempting assumption is that the queue retained the work because it retained the message. That assumption is wrong: a queue message retains intent, not an external call's result. This is the exact boundary the artifact record closes.

No bytes, no guarantee.

## Failure boundaries and observability

The state model should name outcomes rather than collapse them into `failed`. Useful states are `generation_pending`, `generation_limited`, `artifact_staged`, `persistence_limited`, `committed`, and `terminal`. Store the attempt count and next eligible time per transition, not as one shared counter. A storage throttle should not consume the generation retry budget.

Record structured events with `job_id`, `asset_id`, `tenant_id`, `product_id`, transition, attempt, dependency class, response class, and scheduled delay. Never log image bytes, signed retrieval locations, credentials, or raw customer prompts. Metrics should separate generation throttles from persistence throttles, show queue age rather than queue depth alone, and count artifacts stuck between staging and commitment. That middle-state age is the signal that catches a pipeline producing images faster than it can safely publish them.

Exports deserve their own audit trail. The export job should snapshot or otherwise record the exact committed asset IDs selected under the authorized tenant, then build the archive from that manifest. This prevents a long-running export from silently changing membership as products are edited. It also makes a missing object diagnosable: the manifest says what should exist, while the object store says what can be fetched.

For a downloadable archive, construct the `Content-Disposition` response header at the delivery boundary, using a server-generated filename rather than unchecked tenant input. MDN documents the `attachment` disposition and `filename`/`filename*` parameters, including browser behavior that matters when filenames contain non-ASCII characters. This is separate from object naming; an internal storage key does not need to become the customer's download filename.

## Architecture options

| Option | Recovery after generation succeeds | Tenant-isolation surface | Operational cost | Decision |
|---|---|---|---|---|
| One queue job performs generation and final upload | Depends on bytes surviving the same worker attempt | One handler mixes auth, generation, and storage state | Few components, ambiguous retries | Reject for the marketplace path |
| Split transitions with a durable artifact | Later workers persist the same artifact | Tenant identity is fixed in the artifact record and rechecked at commit | Extra state and cleanup policy | Choose |
| Regenerate after any failure | Creates another provider-side result | New attempts can drift from the original asset record | Simple queue behavior, duplicate work and reconciliation | Use only for disposable outputs |

The chosen design isn't free. Durable staging consumes capacity, requires retention and deletion rules, and creates an additional access-control boundary. It is not suitable when images are disposable previews, generation is deterministic under an explicitly verified contract, and occasional regeneration is acceptable. In that narrower case, a single job with an idempotency key and a deterministic final key can be the more honest design.

For regulated workloads, don't infer authorization from an architectural diagram or a product category. The service boundary, deployment, and inherited controls determine what is covered; procurement teams can use the official FedRAMP program site to verify the relevant authorization record. Most marketplace image pipelines won't need that process, and adding its vocabulary to an ordinary design review does not improve tenant isolation.

## Critical path in Python

The code below is deliberately an orchestration core, not a storage SDK tutorial. `jobs`, `generator`, `artifacts`, and `objects` are interfaces whose contracts must be tested against the selected implementations. The important part is that the retry target follows the stored transition and that all ownership inputs come from the claimed job record.

```python
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
import hashlib
import random


@dataclass(frozen=True)
class ClaimedJob:
    job_id: str
    asset_id: str
    tenant_id: str
    product_id: str
    transition: str
    attempt: int


class RateLimited(Exception):
    def __init__(self, retry_after_seconds: int | None = None):
        self.retry_after_seconds = retry_after_seconds


def retry_delay(attempt: int, retry_after_seconds: int | None) -> timedelta:
    if retry_after_seconds is not None and retry_after_seconds >= 0:
        return timedelta(seconds=min(retry_after_seconds, 900))

    ceiling_seconds = min(2 ** min(attempt, 8), 300)
    return timedelta(seconds=random.uniform(0, ceiling_seconds))


def process(job: ClaimedJob, jobs, generator, artifacts, objects) -> None:
    # Ownership is loaded with the claim; callers cannot replace these fields.
    jobs.assert_product_owner(job.product_id, job.tenant_id)

    try:
        if job.transition == "GENERATE":
            result = generator.create(asset_id=job.asset_id)
            digest = hashlib.sha256(result.bytes).hexdigest()
            artifacts.stage(
                asset_id=job.asset_id,
                tenant_id=job.tenant_id,
                payload=result.bytes,
                sha256=digest,
            )
            jobs.advance(job.job_id, expected="GENERATE", next_transition="PERSIST")
            return

        if job.transition == "PERSIST":
            artifact = artifacts.get(job.asset_id, tenant_id=job.tenant_id)
            key = (
                f"tenants/{job.tenant_id}/products/{job.product_id}/"
                f"{job.asset_id}.png"
            )
            objects.create_if_absent(
                key=key,
                payload=artifact.payload,
                sha256=artifact.sha256,
            )
            jobs.commit(job.job_id, key=key, sha256=artifact.sha256)
            return

        raise ValueError(f"unsupported transition: {job.transition}")
    except RateLimited as error:
        delay = retry_delay(job.attempt, error.retry_after_seconds)
        jobs.reschedule(
            job.job_id,
            transition=job.transition,
            next_attempt_at=datetime.now(timezone.utc) + delay,
        )
```

The repository operation `advance` must be conditional on the expected state, while `commit` must bind the final key and checksum to the same tenant-scoped asset record. Those are database transaction requirements. The generator and object store cannot share that transaction, which is why reconciliation still exists: periodically find staged artifacts past their expected commit time, verify the tenant-scoped record, and enqueue `PERSIST` without invoking generation.

Test the ugly interleavings. Deliver the same message twice. Stop a worker after staging but before `advance`; stop it after object creation but before `commit`; return `429` independently from each dependency; change a product's tenant reference and verify the ownership assertion blocks the job; run two export workers against the same manifest. The pass condition is convergence on one committed database record and one verified object, not merely a green queue dashboard.

## Rejected design and its valid use case

The rejected design is a single queue handler that calls the generator, uploads the response, and retries the whole function on any exception. Its appeal is real: fewer states, fewer repositories, and a shorter happy path. For disposable thumbnails that can be regenerated, are never exported as contractual customer data, and have no cross-tenant reuse, that trade can be reasonable.

It is the wrong default for marketplace product media. Product images participate in listings, moderation, cache invalidation, deletion, and tenant-scoped exports; losing the distinction between "created" and "committed" makes each downstream workflow guess. The split-transition design pays for one explicit artifact lifecycle so those consumers can rely on a single commitment point.

Keep the limitation visible: this design provides idempotent convergence only to the degree that the artifact store, database conditions, and object-create precondition honor their contracts. Your mileage may vary across adapters. Run failure-injection tests during deployment, retain transition-level telemetry, and set an explicit terminal policy rather than assuming retries eventually win.
